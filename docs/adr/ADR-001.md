# ADR-001: Database per Service

## Status
Aceito — implementado (`docker-compose.yml`: `postgres-user`, `postgres-order`, `postgres-payment`, `mongodb`).

## Contexto
O case modela um e-commerce simplificado com 4 microsserviços independentes
(User, Order, Payment, Notification), cada um dono de um bounded context
próprio. Para que a independência de deploy e evolução de schema seja real
— e não apenas nominal — é preciso decidir se os serviços compartilham um
único banco de dados ou se cada um tem o seu.

Um banco único, compartilhado entre os 4 serviços, é o caminho mais simples
no curto prazo (menos containers, uma única conexão, possibilidade de JOIN
entre dados de serviços diferentes), mas acopla os serviços pelo schema:
uma migration em um serviço pode quebrar outro, e o deploy independente —
um dos pontos centrais que este case pretende demonstrar — deixa de ser
possível na prática.

## Decisão
Cada serviço é dono exclusivo do seu próprio banco de dados. Nenhum serviço
acessa diretamente o schema ou as tabelas de outro; toda troca de dados
entre serviços acontece via API REST síncrona ou evento Kafka assíncrono
(regra já registrada no `CLAUDE.md` como inviolável).

Na implementação atual:
- **User Service** → PostgreSQL dedicado (`postgres-user` / `user_db`)
- **Order Service** → PostgreSQL dedicado (`postgres-order` / `order_db`)
- **Payment Service** → PostgreSQL dedicado (`postgres-payment` / `payment_db`)
- **Notification Service** → MongoDB dedicado (`notification_db`), escolha
  proposital de tecnologia diferente dos demais (ver seção de Technology
  Diversity em `docs/arquitetura.md`)

Os três Postgres rodam como containers separados no `docker-compose.yml`,
cada um com seu próprio volume, usuário e senha vindos de variáveis de
ambiente (`.env`) — sem script de inicialização multi-database, evitando
qualquer mecanismo de bootstrap compartilhado entre os bancos.

### Alternativa rejeitada
**Banco compartilhado único** para os 4 serviços — rejeitado por acoplar
deploys e schemas entre serviços que deveriam evoluir de forma
independente, contrariando o objetivo central do case.

## Consequências

**Positivas**
- Deploy e evolução de schema de cada serviço são verdadeiramente
  independentes — uma migration no Order Service não tem como quebrar o
  User Service.
- Falha ou indisponibilidade de um banco não derruba os demais serviços.
- Permite demonstrar *polyglot persistence* na prática (PostgreSQL
  relacional para User/Order/Payment, MongoDB orientado a documento para
  Notification).

**Negativas / trade-offs aceitos**
- Não há transação ACID nem JOIN entre dados de serviços diferentes;
  operações que cruzam serviços (ex.: pedido → pagamento → notificação)
  dependem de consistência eventual e do padrão de coreografia via Kafka
  (ver `docs/arquitetura.md`, seção de comunicação assíncrona).
- Mais containers para subir e operar localmente (3 instâncias de
  PostgreSQL em vez de uma).
- Consultas que hoje seriam um JOIN simples em um banco único precisam ser
  resolvidas por composição via API entre serviços ou por dados
  duplicados/desnormalizados quando fizer sentido.
