# ADR-007: Spring Boot 4.1 em vez de 3.5

## Status
Aceito — implementado (`pom.xml` raiz).

## Contexto
No setup inicial do projeto (ADRs anteriores e `docs/arquitetura.md`), a
stack fixou Spring Boot 3.5.16 — a última versão estável da linha 3.x.
Entre a auditoria do ambiente e este registro, dois fatos mudaram a
equação:

- Spring Boot 3.5 encerrou o suporte open-source em 30/06/2026 (não
  recebe mais patch de CVE gratuito).
- Spring Boot 4.1 é o GA atual, com suporte até 31/07/2027, e conta com
  Spring Cloud 2025.1.2 ("Oakwood") como primeiro release train
  compatível.

Levantamento prévio (research, não registrado como ADR até esta decisão)
identificou o custo de migrar para 4.1 no nosso escopo específico
(Gateway, Security + JWT, Kafka, JPA), incluindo breaking changes em
Spring Security 7 (defaults de CSRF, validação de JWT), Hibernate 7.1,
Spring for Apache Kafka 4, e riscos em Testcontainers 2.0 e na
integração OpenTelemetry/Micrometer.

O ponto decisivo: o projeto está em estágio greenfield — nenhum serviço
tem código de negócio implementado ainda (nenhuma entidade, controller,
teste). Praticamente todo o custo levantado é custo de **migração de
código já escrito**, que não existe neste momento. Escrever direto contra
a API do Boot 4.1 custa perto de zero a mais do que escrever contra a do
3.5; adiar a decisão significaria pagar esse mesmo custo de migração mais
tarde, em cima de código e testes já existentes, além de rodar por mais
tempo numa versão sem patch de segurança gratuito.

## Decisão
Adotar Spring Boot **4.1.1** (última patch estável da linha 4.1) e Spring
Cloud **2025.1.2** ("Oakwood") como stack base do projeto, substituindo
3.5.16 / 2025.0.3 definidos anteriormente.

Alterado nesta implementação:
- `pom.xml` raiz: `spring-boot-starter-parent` → `4.1.1`;
  `spring-cloud.version` → `2025.1.2`.
- `api-gateway/pom.xml`: nenhuma mudança necessária — já usava o artefato
  correto e atual `spring-cloud-starter-gateway-server-webflux`
  (o artefato antigo `spring-cloud-starter-gateway`, que foi removido no
  train 2025.1, nunca chegou a ser usado neste projeto).
- `mvn clean install` validado com sucesso nos 6 módulos (parent +
  api-gateway + user/order/payment/notification-service) após a troca.

### Alternativa rejeitada
**Permanecer em Spring Boot 3.5.16** até a Fase 1 estar implementada e só
então avaliar a migração — rejeitada porque adiar inverte o argumento
de custo: hoje a migração é gratuita (não há código pra migrar); feita
depois, o mesmo conjunto de breaking changes teria que ser aplicado em
cima de entidades, controllers, configuração de segurança e testes já
escritos.

## Consequências

**Positivas**
- Base construída direto sobre a API atual (Spring Framework 7, Jakarta
  EE 11, Hibernate 7.1, Spring Security 7), sem passivo técnico de
  migração acumulado.
- Janela de suporte OSS mais longa (4.1 até 31/07/2027, contra 3.5 já em
  EOL), incluindo patches de CVE.
- Recursos novos disponíveis desde já: `@ServiceConnection` nativo para
  Testcontainers no Boot 4.0+, Kafka 4.x client com KRaft (já alinhado
  com o `apache/kafka:4.1.2` do `docker-compose.yml`), suporte a
  variáveis de ambiente do OTLP SDK exporter no 4.1.0.

**Negativas — riscos aceitos conscientemente**
- **Propagação de contexto de trace em threads assíncronas no fluxo
  Kafka**: a integração Micrometer/OpenTelemetry tem problemas
  documentados de contexto de trace vivendo em `ThreadLocal`, que não
  acompanha o trabalho quando ele salta pra uma thread nova — exatamente
  o padrão do nosso fluxo Order → Kafka → Payment → Kafka → Notification.
  Isso pode complicar a Fase 5 (Observabilidade / tracing distribuído) e
  exigir propagação manual de contexto nos listeners Kafka, algo que não
  seria necessário (ou seria mais simples) numa stack mais madura em
  3.5.x. Aceito porque a Fase 5 ainda está longe no roadmap e dá tempo de
  investigar/mitigar antes de chegar lá.
- **Testcontainers 2.0 com breaking changes**: a versão de Testcontainers
  que acompanha a integração nativa do Boot 4 introduz renomeação de
  módulos (prefixo `testcontainers-`), realocação de classes de
  container e remoção total de suporte a JUnit 4. Bibliotecas de
  terceiros que dependem de Testcontainers (ex.: `testcontainers-spring-boot`
  da Playtika) ainda não foram atualizadas para essa combinação no
  momento deste registro. Isso pode nos forçar a escrever configuração
  de Testcontainers mais manual/verbosa na Fase 1 (testes de integração
  do User Service) do que o esperado, ou evitar libs de terceiros que
  ainda não acompanharam a migração.
- Menor volume de conteúdo de terceiros (tutoriais, Stack Overflow,
  exemplos) para Boot 4.1 comparado a 3.x, por ser release recente —
  depuração de problemas não documentados nos search acima pode exigir
  ler código-fonte/issues do próprio Spring em vez de achar resposta
  pronta.
